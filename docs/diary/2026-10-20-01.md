# Diary — 2026-10-20 (1)

## Registering the interaction work: selection, clicks, folding, a bounded input

The owner, reviewing a prototype of ask's screen, asked for text selection across what is drawn (copied to the clipboard,
tunable, kept across a scroll), click actions on components, images and long code that can fold into a placeholder, and an input
bounded in rows that scrolls inside itself. They said it belongs in TerminalKit, with the policy in ask's settings, and that it
needs studying across ask before it is built. This records what the source says today and what was registered. **Nothing was
built and no terminal was probed.** Decision: ADR-0027. Entries: roadmap 0016 to 0019. The ask side: its roadmap 0051 and ADR-0044.

### What the source says (read, and checked with greps, not run)

| Claim | How checked | Verdict |
|---|---|---|
| Mouse decoding and a session mode exist | `MouseDecoder` (SGR 1006 and 1016), `InputEvent.mouse`, `TerminalModes.mouse` (`?1000 ?1002 ?1006`) | **CONFIRMED** |
| Nothing above the decoder handles a mouse event | grep of `Sources` for mouse handling outside the codec, the input event, the modes, the session and the router | **CONFIRMED**: no hits |
| A selection type exists, in character offsets | `TextSelection` with `TextPosition(row, col)`; `extractText` uses `line.index(offsetBy:)` | **CONFIRMED** |
| The kit can convert a display column to a character offset | `TextDisplayMetrics.characterOffset(forDisplayColumn:in:tabSize:)` and its inverse | **CONFIRMED** |
| Selection does not use that conversion | grep for callers of both conversions and of `extractText` in `Sources` | **CONFIRMED**: no caller in the package. They are public API, so another app may call them; **not searched** |
| `TextWrap` returns no source ranges | `TextWrap.lines(_:width:)` returns `[String]` | **CONFIRMED** |
| A keep-the-cursor-visible viewport exists in the kit | `TextNavigation.ensureVisible(cursor:visibleRows:visibleCols:wrapLines:)` | **CONFIRMED**; no caller in the package; it works on hard lines |
| OSC 52 can be written and its reply parsed | `EscapeSequences.setClipboard`, `OSCClipboard.parse` (including kitty's empty reply for a declined read) | **CONFIRMED** |
| A kitty graphics encoder exists, and no image belongs to content | `GraphicsEncoder`, `GraphicsCommand`; `PixelChrome` draws lines and bars | **CONFIRMED** |
| ask uses none of the kit's text editing types | grep of ask's `Sources` for `TextBuffer`, `TextCursor`, `TextNavigation`; `PromptEditor` imports `TerminalKitText` and uses none | **CONFIRMED**: its editor is a parallel implementation, with a hard-coded `maximumPromptRows` of six |
| ask has no mouse or clipboard handling | grep of ask's `Sources` for mouse, clipboard, pasteboard and OSC 52 | **CONFIRMED**: no hits |

### What went wrong

- **My first draft of two entries was wrong, in the kit's favour.** I wrote that selection lacked a column-to-offset conversion and
  that a bounded input would have to be promoted from ask. Both existed in the kit and were unused: the conversion in
  `TextDisplayMetrics`, the viewport primitive in `TextNavigation`. I found it by opening the neighbouring files before
  committing. Roadmap 0017 and 0019 now say what is there and what is missing.
- **I began on the main checkout instead of a worktree** and undid it before writing anything.

### Not verified

Every terminal fact the design depends on: whether Terminal.app accepts OSC 52, the payload ceiling of each terminal, which
modifier returns a terminal's own selection while mouse reporting is on, what each does under tmux and over ssh, and the cost of
re-placing images each frame while scrolling. Each entry names the probe that comes first.
