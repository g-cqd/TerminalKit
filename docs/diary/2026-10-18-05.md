# Diary — 2026-10-18 (05)

## The signal handler never fired, and installing it was worse than the bug

Found from `ask`'s side: roadmap 0006 wanted the reset ladder applied on a shutdown signal, and
`TerminalKitInput.SignalHandler` already existed. So it got wired, and the PTY probe said no.

| Configuration | Result on a real `SIGTERM` |
|---|---|
| no handler | killed by `SIGTERM` — dies, terminal **not** restored |
| `SignalHandler` wired | **ignores `SIGTERM`** — still running after 4 s, needs `SIGKILL` |

`DispatchSource.makeSignalSource(signal:queue:)` was given `.main`, and a terminal program blocks its
main thread in `read(into:)`. The main queue never turns, the continuation never yields, and the
process stops responding to `SIGTERM`.

**This is the second time in two days that something returned successfully and did nothing.** The first
was `ask`'s own emulator harness, which reported PASS with every tier a no-op. Same shape, same lesson:
something that appears to work and does not is worse than nothing, because it reads as handled.

## The fix, and how it was verified

A `sigaction` handler now does the least async-signal-safe thing possible — one `write` of one byte to
a pipe — and a dedicated Foundation `Thread` blocks in `read` on the other end. Neither the main thread
nor a cooperative pool thread is involved. `SA_RESTART` is deliberately unset so a blocked `read`
returns `EINTR`.

Six tests, event-driven through Aemi's `AsyncEventProbe`. No `Task.sleep`, no `Task.yield`, no polling,
no wall-clock assertion. **The suite runs in 0.001 s**, so there is nothing to flake.

### The clock choice, argued rather than assumed

`AsyncEventProbe` accepts an injectable clock, and under a `TestClock` the wait ends **only** when the
event arrives. That is maximum determinism — and a hang forever if delivery ever breaks again.

I built it that way first, and it hung the suite. Which is the right answer for a task whose completion
is under test control, and the wrong answer for an OS signal: a hang in CI is indistinguishable from a
busy machine and diagnoses nothing. So the tests use the `ContinuousClock` convenience overload with a
generous deadline that never fires in practice, and a broken handler fails with a named
`AsyncEventProbeTimeoutError`.

That is determinism traded for a diagnosable failure, deliberately.

### Verified end to end, not only in a unit test

`ask` built against the local TerminalKit, wired to the handler, on a PTY:

    in raw mode at the moment of the signal: True
    exited: signaled=False code=143
    raw mode afterwards : True
    leaves alt screen   : True
    shows cursor        : True
    disables mouse      : True
    disables paste      : True

Exit **143** is `128 + SIGTERM` — the shell convention, which the old callback signature could not
produce because it never reported which signal fired. `termios` restored, alternate screen left, cursor
shown, mouse and bracketed paste disabled. That is exactly what `ask`'s roadmap 0006 asked for.

## Two guards, one of which caught my own error

Breaking the drain branch turns the resize test red with a named error. Good.

An earlier attempt to break it produced **zero failures** — because it was a compile error, not a
behavioural change. That is the fourth time this month a "probe" turned out incapable of failing, and it
is the reason every guard in this repository is broken on purpose before it is trusted.

## Still owed in this repository

  Terminal.app when `KITTY_WINDOW_ID` is inherited from a launching kitty session. Measured, recorded in
  `ask`'s roadmap 0003, still unfixed here.
- The standards pass the user asked for — near-zero `@unchecked Sendable`, `@concurrent`/`nonisolated`

  tests with no `Task.yield` — is **not yet done**. Four justified `@unchecked Sendable` sites exist and

  in both this repository and `ask`.
- TerminalKit's white paper still carries the module-count claim `ask` has already corrected, which
  contradicts this repository's own ADR that the two laws must not diverge.
