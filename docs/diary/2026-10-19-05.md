# Diary — 2026-10-19 (05)

## Probing keyboard support without blocking startup

Adopting `TerminalSession` in ask needs `keyboardProtocol`. The only probe, `TerminalProbe`, costs 520 ms
on a silent terminal (ADR-0014), so the first adoption would have bought unambiguous Escape with half a
second of cold start on Terminal.app. Decision: ADR-0020.

| Claim | Probe | Verdict |
|---|---|---|
| Every terminal we target answers primary device attributes | `CSI ? u CSI c` in kitty, ghostty, wezterm, Terminal.app | **CONFIRMED**, Terminal.app included (`CSI ? 1;2 c`) |
| The keyboard reply comes before device attributes | same, five trials each | **CONFIRMED** on kitty and ghostty; wezterm and Terminal.app send device attributes only |
| The round trip fits a startup budget | same | **Mostly**: under 3 ms on kitty, ghostty and Terminal.app once warm, 19 ms on kitty's first query, 8–16 ms on wezterm. Not waited on, so it does not matter |
| The router hands both replies over as `.unknown` | `TerminalSessionProbeTests` route real reply bytes | **CONFIRMED** |
| `InputSource` can change its Escape reading mid-stream | negative control: a setter that ignores the value | **CONFIRMED**: the test fails with it |

Red: six expectations failed against a stub `observe` that returned `false`. The first green still failed
one: device attributes arriving after a keyboard reply were passed through as input. The session now
waits for device attributes as the end of the probe whatever came first.

`InputSource`'s read loop captures a small `AtomicFlag` rather than `self`, so the change does not extend
the source's lifetime.
